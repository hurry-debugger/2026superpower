# AI 协作与人工审批流程

## 1. 固定工作顺序

1. 读取 `AGENTS.md`、`docs/handoff.md`、相关规范和实际文件。
2. 只读分析，确认现状、文件来源、已有改动和验证环境。
3. 在对话中提交下述逐文件修改清单，等待用户明确批准。
4. 仅实施批准范围内的内容；发现新需求、增加文件或改变约定行为时暂停相关修改，重新说明。
5. 使用批准的验证方式检查，报告结果与未执行项目；Git 留给用户人工处理。

用户批准某份完整计划，即授权按该计划列明的文件和内容实施，无需重复索取相同批准。
批准不能自动扩大到其他任务、未列出的文件、安装工具或 Git 操作。

## 2. 修改前必须在对话中列出的信息

| 项目 | 应说明的内容 |
| --- | --- |
| 目标 | 本轮解决的问题及可观察结果 |
| 文件与位置 | 新增/修改/删除/移动的具体路径，已有文件的函数、段落或配置项 |
| 详细内容 | 新增什么、修改什么、为什么需要，不只写“优化”“整理” |
| 影响 | 接口、调用关系、时序、单位、参数、构建或硬件行为是否变化 |
| 边界 | 是否涉及生成文件、原有改动、外部工具、产物及临时文件 |
| 验证 | 执行什么、预期结果、产物位置，以及不能验证的内容 |
| 交接更新 | 是否修改 `docs/handoff.md`、决策或测试文档 |

新增或重命名自维护 C/H 时，清单必须包含 Keil `.uvprojx` 的分组、C 文件编译条目、
H 文件登记及头文件路径。普通模块登记沿用既有目标与编译选项，不通过修改 `.ioc` 实现。
源文件应参与编译；头文件登记用于工程浏览。是否加入启动流程或中断调用需另行明确。

在用户明确同意前不得执行文件写入、自动格式化、转码或“顺手修复”。
批准范围内为达到已批准行为所需的修正可继续；实质变化必须重新说明并等待批准。

## 3. 生成文件与 CubeMX

禁止直接编辑 `.ioc`。CubeMX 生成代码仅允许在获批的 `USER CODE BEGIN/END` 区域内部
编写自维护代码，区域外内容及标记行保持原样；不得自行创建或移动标记。
需要更改外设配置时，在对话中提出 CubeMX 配置项、预期生成差异和验证方法，获得单独批准后
才操作 CubeMX。若当前工具无法使用 CubeMX，应报告限制，不回退到文本编辑配置或区域外代码。
普通文件修改清单的批准不授权修改区域外内容，厂商驱动及生成启动/RTE 文件仍不得直接改写。

模块接入须先审阅具体文件、USER CODE 区域、调用顺序、影响和验证方法，再取得批准。
写入前保存基线，写入后逐字节核对区域外内容及标记行不变，不整文件格式化或转码。
来源不明时先检查生成标记、工程配置和版本记录，仍不能确认则向用户说明。

## 4. 验证、异常与 Git

- 先记录既有改动；默认以文本、语法、名称及构建配置等静态检查验证，不编写测试脚本。
  用户特别说明时才增加或执行专项测试；已有测试按需维护，不默认删除。
- 内容检查和格式检查只读运行；禁止直接用 `clang-format -i` 或其他写回功能代替审阅。
- 构建、测试可能生成文件时，需要事先说明位置和范围；`python -B` 避免生成 `__pycache__`。
  明确获批的主机专项测试仅在系统临时目录生成产物，结束清理；静态检查不冒充固件编译通过。
- 发现生成文件或原有文件发生非预期变化，停止相关操作，报告差异；不自行覆盖或回退。
- 不安装钩子、依赖或工具，不自动暂存、提交、推送，不创建分支或 worktree。
- 对已批准范围以外的缺陷，说明现象、证据及建议，等待新批准后再改。

## 5. 状态与交接

`docs/handoff.md` 是当前状态入口，不堆积完整聊天记录。获批更新时保留：

- 当前目标、完成范围和未完成事项。
- 实际改动及原有工作区改动的区别。
- 检查命令、日期、结果和局限；静态、编译、上板证据分别记录。
- 已知问题、待用户确认事项及下一步明确入口。

长期约定写入 `docs/decisions.md`；硬件事实写入 `docs/hardware.md`；测试方法写入
`docs/testing.md`。不要建立多个互相矛盾的“最新状态”。
如果本轮未获文档写入批准，则在对话里提供交接信息，不自动保存。
